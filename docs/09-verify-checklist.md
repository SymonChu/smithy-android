自动化测试能守住的都守住了（113 个用例）。剩下这些**只有真机能证明**，按依赖顺序排列：
前面的不过，后面的不用试。

每条都写了「怎么做 / 预期 / **失败了往哪查**」——最后一项最重要：这些功能的失败症状

### 0.1 用 Smithy 打开外部包（别跳过这条）

**怎么做**：在文件管理器里长按一个 apk → 「打开方式」→ 选 Smithy。或者从聊天软件里「分享到」Smithy。

**预期**：App 起来后**直接进工作台并开始解包那个包**。

**失败往哪查**：App 起来了但停在空标签页 → 外部的 `ACTION_VIEW` / `ACTION_SEND` 没接上（`MainActivity.incomingUriOf`）。
**这条是 M4 验收的第一步**——「从 QQ 收到 apk」的正常路径就是走这里，而不是先手动导入。

## 1. 签名链路（先验这个，它是所有改包功能的地基）

- **测试包**：第一次建议用**你自己打的包**（有源码、知道原来长什么样），别一上来拿别人的。
- **先备份**：Smithy 不覆盖原包（另存为），但原包还是先留一份。
- **随身工具**：`apksigner verify --verbose <apk>`（Android SDK build-tools 里有）。它判 `Verifies` 是真机能装的关键信号。

### 1.1 `minSdk ≥ 24` 的包

| | |
|---|---|
| **怎么做** | 工作台打开包 → 概览改个应用名 → 打包 → 签名 → 装机 |
| **预期** | 装上了，桌面名字是新的 |
| **失败往哪查** | 报 `INSTALL_FAILED_INVALID_APK` → 看第 1.3 条；报签名冲突 → 先卸载旧版 |

### 1.2 `minSdk < 24` 的包（**v1 签名是自己实现的，最想看这条**）

| | |
|---|---|
| **怎么做** | 同上，但打开一个 `minSdk 21` 的包（或先用概览把 minSdk 改成 21 再打包） |
| **预期** | 同样装上 |
| **失败往哪查** | `INSTALL_PARSE_FAILED_NO_CERTIFICATES` / `NO_SIGNATURES` → v1 那三个文件有问题（`META-INF/MANIFEST.MF`、`SMITHY.SF`、`SMITHY.RSA`）；先跑 `apksigner verify --min-sdk-version 21 --max-sdk-version 23` 看它说什么 |

### 1.3 zip 对齐（**上次真机踩过的**）

| | |
|---|---|
| **怎么做** | 改完包装机，特别是有 `.so` 的包（游戏、含原生库的 app） |
| **预期** | 装上并能启动 |
| **失败往哪查** | `Failed to extract native libraries, res=-2` → **`.so` 的 16KB 页对齐丢了**。命令-line 体检：`zipalign -c -P 16 -v 4 <apk>` |

## 2. 改包功能

### 2.1 换图标

| | |
|---|---|
| **怎么做** | 工作台 → 图标 → 选一张图 → 应用 → 打包签名装机 |
| **预期** | 桌面图标换了；**启动 app 不崩** |
| **失败往哪查** | 换完崩 → 多半是图标资源被写坏了，看是不是原包是 adaptive 图标（那种要动前景层，比换普通图标复杂）；用「矢量图/无图标声明」的包更简单，先拿那种试 |

### 2.2 `assets/` 文本编辑

| | |
|---|---|
| **怎么做** | 文件 → 打开 apk → 进 `assets/` → 找一个 `.txt`/`.json` → 编辑 → 保存 → 保存到新的 apk → 签名装机 |
| **预期** | 装上了；如果那个文件被 app 读取（比如配置），行为随之改变 |
| **失败往哪查** | 保存时提示「看着不是文本」→ apk 里的 xml 是**二进制**格式，要用工作台的资源功能改，不是文本编辑器；装机后崩 → 文本编码问题，确认原文件是 UTF-8 |

### 2.3 批量改名（**先在测试目录试，别拿重要文件**）

| | |
|---|---|
| **怎么做** | 文件 → 进一个自己造的测试目录 → 多选 → 设规则 → 看预览 → 应用 |
| **预期** | 预览里显示的就是实际结果；撞名时不给执行并说明原因 |
| **失败往哪查** | 结果和预览不一致 → 这是最严重的一类，请把「规则 + 选择 + 预览 + 实际结果」都发我 |

## 3. AI 助手

### 3.1 一句话完成一轮改动

| | |
|---|---|
| **怎么做** | 对话 → 选包 → 说「把应用名改成 xxx，打包签名」 |
| **预期** | 模型调工具；写操作前弹确认条（除非开了信任模式）；diff 逐行显示改了什么；最后产出一个可安装的包 |
| **失败往哪查** | 一直转圈 → 检查「设置」里的 baseUrl / key / 模型名（OpenAI 兼容的三件套）；说「没有打开包」 → 先在对话页点「选包」 |

### 3.2 门控

| | |
|---|---|
| **怎么做** | 在**没开**信任模式时让它改点东西；然后在设置里开信任模式再来一次 |
| **预期** | 第一次每步都问；开了之后写操作不再问，但**装机/删除仍然问** |
| **失败往哪查** | 开了信任模式后连删除都不问了 → 不该发生，请立刻告知（`DESTRUCTIVE` 永远要确认是设计上的硬约束） |

## 4. 已知的、不该当成 bug 的现象

- **改过内容的包签名一定失效** —— 必须「改 → 打包 → 签名 → 装」，少了签名那步必报签名错。
- **改过资源的包体积会变**（约 +0.6%）—— ARSCLib 重排资源表导致，正常。
- **apksig 的 `ApkVerifier` 对 `targetSdk 35` 的包会多报一条「MANIFEST 主属性段摘要不匹配」**
  （`Expected`/`actual` 都打印 `null`）—— 库自身的误报，官方 `apksigner` 对同一产物判
  `Verifies`。Smithy 内部的验签已按 `apksigner` 的判据走，所以界面显示正常。

## 5. 出问题时给我什么信息

1. **原样贴报错**（整段，别概括）——上次就是靠这行字找对了方向
2. **哪一步**（改包 / 打包 / 签名 / 装机 / 启动）
3. **包的来源**（自己打的 / 下载的 / 系统 app）和它的 `minSdk` / `targetSdk`
4. 有条件的话，`apksigner verify --verbose <产物>` 的输出
